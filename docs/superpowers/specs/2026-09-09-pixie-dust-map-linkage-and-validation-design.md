## 1. 背景与核心痛点

用户在游轮上实际使用仙尘（Pixie Dust）功能进行回礼扫楼时，发现以下痛点严重影响了操作效率：
1. **不自动排序（扫楼极不方便）**：
   - 目前“收到列表”仅按礼物等级和时间倒序排序，同一楼层的房间完全打散，用户无法顺着走廊门牌号一路回礼；
   - 用户在回礼时必须在列表里看一整圈，费力统计“这层要回谁、要回几个”，体验割裂。
2. **联动检视页面简陋且不明显**：
   - 当前的 `LinkageViewDialog` 仅为一个狭窄的灰色弹窗，只有基础纯文本对照，缺乏楼层聚合、统计概览、视觉层级和状态区分。
3. **无法与地图页面联动**：
   - 用户回礼时找不到房间位置，必须退出仙尘模块，切到甲板地图去搜索房号；
   - 极度需要一种**联动跳转功能**：点击一键跳转到对应甲板地图，将本层所有“已回过礼”、“没回过礼”、“回过但送的数量>回的数量（需补礼）”的房间全部在地图上用三色醒目标注出来。
4. **键盘 Deck 下拉冗余**：
   - 键盘录入需要先从下拉菜单选 Deck，再输入 3 位房号。实际乘客更习惯直接按出 4 位或 5 位完整房号（如 `6012`、`11216`），手动切 Deck 多此一举。
5. **缺少实时客房核验**：
   - 用户输错房号时无提示，容易将不存在的房间写入数据库。项目已有全船 2,111 间客房的 `StateroomCatalog`，应在输入阶段实时核对并在地图不存在时即时报警。

## 2. 核心架构与功能设计

### 2.1 模块一：键盘直输全房号与实时验房 (`PixieDustKeypad.kt`)

#### 1. 交互与布局升级
- **移除 DeckDropdown**：移除原先的顶部下拉菜单，释放垂直空间。
- **全房号直接输入**：
  - 支持直接敲击数字键输入 4 位（如 `6012`）或 5 位（如 `11216`）房号，最大长度为 5。
  - 保留“清空”、“退格”操作。

#### 2. 房号智能解析 (`parseStateroomInput`)
- **4 位数字**（如 `6012`）：首位 `6` 解析为 `deck = 6`，后 3 位 `012` 为 `room = "012"`。
- **5 位数字**（如 `11216`）：前两位 `11` 解析为 `deck = 11`，后 3 位 `216` 为 `room = "216"`。
- 提取全房号字符串 `fullRoom = "$deck$room"`。
- **兼容性**：数据库 `PixieDustEntity` 继续保持 `deck: Int, room: String` 结构，既有数据 100% 兼容。

#### 3. 实时客房校验与视觉反馈
- 输入长度在 1~3 位（输入未完成）：
  - 房号大字正常展示已输入数字，下方显示灰色小字 `请输入 4 或 5 位客房号`；
  - “记一笔”按钮禁用。
- 输入达到 4 或 5 位：
  - 调用 `StateroomCatalog.getAllStaterooms()` 进行精准匹配：`rooms.any { it.roomNumber == fullRoom }`。
  - **校验通过（地图存在该房间）**：
    - 大字下方显示绿色微章：`✓ Deck {deck} 客房有效`；
    - 自动拉取该房间的历史发出等级，有历史则自动预选；
    - 用户选定等级后，“记一笔”按钮变蓝激活。
  - **校验失败（地图不存在此房间）**：
    - 大字下方显示醒目红色告警文本：`⚠️ 地图上无此房间，请核对`；
    - “记一笔”按钮严格禁用，阻止脏数据入库。

### 2.2 模块二：扫楼顺号排序与状态筛选 (`PixieDust.kt`, `PixieDustLists.kt`)

#### 1. 扫楼动线优先排序（Deck + Room 升序）
- 针对回礼扫楼场景，新增排序与归组模式：
  - **收到列表（ReceivedList）排序规则**：
    1. 优先按 **Deck（楼层数字）升序**（如 Deck 6 -> Deck 7 -> ... -> Deck 11）；
    2. 同一楼层内部按 **Room（房号数字）升序**（顺着走廊一路走过去）；
    3. 同一房间内多条记录：**未回礼优先置顶**（按等级价值降序），已回礼沉底。
  - **归组列表（GroupedView）排序规则**：
    - 同样支持按 Deck 升序、Room 升序展示，方便按楼层巡查。

#### 2. 列表快捷状态筛选
- 在列表顶部统计条下方添加轻量筛选切换胶囊：
  - `全部`：展示当前楼层/全部记录。
  - `🔴 待回/需补`：一键过滤出仍需送礼的房间，回礼扫楼时列表干净专注。

### 2.3 模块三：全新联动检视页面 (`LinkageViewSheet.kt`)

告别原先简陋的 `AlertDialog`，重构为现代全屏/大尺寸 `ModalBottomSheet`：

1. **顶部全船概览卡片**：
   - 显示总互赠房间数、已回平房间数、🔴 待回礼房间数、🟡 需补礼房间数。
2. **按楼层（Deck）卡片分组**：
   - 每个楼层独立为一张高质感卡片（如 `Deck 11`）。
   - **楼层卡片头部**：
     - 楼层名称与图标（`Deck 11`）；
     - 状态徽章（如 `待回 3 间 · 需补 1 间 · 已完成 5 间`）；
     - **“🗺️ 查看本层地图” 高亮操作按钮**：点击直接转跳至甲板地图并标注本层所有房间！
3. **房间卡片明细（RoomPair Card）**：
   - 房号标题（如 `11216`）；
   - 三色状态徽标：
     - 🔴 **待回礼**（`未回礼 X 笔`）：对方送了我但我尚未回礼；
     - 🟡 **需补礼**（`收到 X ＞ 发出 Y`）：虽然已回过但对方送得更多，差额需补；
     - 🟢 **已回清**（`发出 ≥ 收到`）：互赠已平衡或我送得更多；
   - 左右两列对比明细：我发出的礼物等级计数 ↔ 对方送来的礼物等级计数；
   - 快捷动作按钮：支持一键跳转地图定位该单间，或快捷打开回礼弹窗。

### 2.4 模块四：地图多房间三色图层联动 (`DeckMap.kt`, `DeckMapScreen.kt`)

#### 1. 路由与数据流转
- 转跳路由参数扩展：
  ```kotlin
  Routes.deckMap(deck = deck, pixieMode = true)
  ```
- 或在 `DeckMapViewModel` 注入 `PixieDustRepository`，当处于仙尘联动模式（或检测到仙尘记录）时，自动拉取当前甲板所有的房间回礼状态：
  ```kotlin
  enum class PixieRoomStatus {
      UNREPLIED,      // 🔴 没回过礼
      NEED_SUPPLEMENT,// 🟡 已经回过，但对方送的数量 > 回的数量
      COMPLETED,      // 🟢 已经回过礼（发出 >= 收到 且无未回项）
  }

  data class PixieRoomMarker(
      val roomNumber: String,
      val status: PixieRoomStatus,
      val unrepliedCount: Int,
      val givenCount: Int,
      val receivedCount: Int,
  )
  ```

#### 2. SVG 地图三色渲染与高亮脚本注入
在 `DeckMapRepository.inlineHtmlWrapperFor(...)` 中追加多房间标注脚本：
- **CSS 样式定义**：
  - 🔴 `.pixie-room-unreplied`：红框呼吸动效 `border: 2px solid #EF4444`，红色定位标记，显示 `🔴 待回`；
  - 🟡 `.pixie-room-supplement`：黄框呼吸动效 `border: 2px solid #F59E0B`，黄色定位标记，显示 `🟡 补礼`；
  - 🟢 `.pixie-room-completed`：柔和绿色常亮边框 `border: 2px solid #10B981`，绿色定位标记，显示 `🟢 已回`。
- **DOM 定位匹配**：
  - 针对每个 `PixieRoomMarker`，在 SVG 中查询对应的客房几何节点（匹配 `rect[id="room-{room}"]`、`polyline[id="outline-{room}"]` 或 `text[id="number-{room}"]`）；
  - 在几何节点外层挂载对应颜色的呼吸发光框，并在房间中心上方悬浮状态小标牌。
- **视野自动聚焦**：
  - 地图加载后，自动计算所有待回（🔴 / 🟡）房间的外接包围盒，将视野平滑滚动态居中至需要回礼的重点区域。

#### 3. 地图界面浮动信息条
- 在 `DeckMapScreen` 顶部常驻仙尘回礼浮动胶囊：
  - 文案：`Deck {deck} 仙尘回礼 · 🔴待回 {u} · 🟡需补 {s} · 🟢已完成 {c}`；
  - 右侧提供“退出标注”或“返回仙尘”按钮，点击便捷返回仙尘记录页。

## 3. 测试与验证计划

### 3.1 单元测试
1. **房号解析与核验 (`StateroomCatalogTest`, `PixieDustTest`)**：
   - 测试 `parseStateroomInput` 解析 4 位（`6012` -> Deck 6, `012`）与 5 位（`11216` -> Deck 11, `216`）；
   - 测试无效格式（非数字、不足 4 位、超过 5 位、14 层等不存在甲板）被拦截；
   - 测试真实 2,111 间客房匹配成功，随机非存在房号（如 `11999`）判定不存在。
2. **扫楼顺号排序 (`PixieDustSortingTest`)**：
   - 测试 `sortForSweepDelivery` 严格按楼层递增 + 房号数字递增排序；
   - 测试同房间内未回礼优先置顶。
3. **房间三色状态判定 (`PixieDustLinkageTest`)**：
   - 发出 0，收到 1 未回 -> `UNREPLIED` (🔴)；
   - 发出 1，收到 2（已回 1，但总数 2 > 1）-> `NEED_SUPPLEMENT` (🟡)；
   - 发出 1，收到 1（已回礼）-> `COMPLETED` (🟢)；
   - 发出 2，收到 1（已回礼）-> `COMPLETED` (🟢)。

### 3.2 仿真与真机验证
1. 打开仙尘记录页，键盘已无 Deck 下拉框。
2. 输入 `11216`，看到实时亮起绿色徽章 `✓ Deck 11 客房有效`，输入 `11999` 看到红色告警 `⚠️ 地图上无此房间` 且记一笔置灰。
3. 进入联动检视，看到卡片式按 Deck 聚合，显示待回/需补/已回统计与房间卡片。
4. 点击 `Deck 11` 卡片右上角的“🗺️ 查看本层地图”，自动跳转至 Deck 11 地图，清晰看到红、黄、绿三色标出的房间呼吸高亮与顶部统计条。
